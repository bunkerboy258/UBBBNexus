# Mass

Mass 下的定位是为了高性能接入 UE Mass 框架的 BBBInstance

适用于由 Mass 管理的子弹 小怪等实例

网络行为遵守网络宪法

输入 状态 行为 表现与网络的职责划分遵循 Actor 的设计思想

数据的物理持有方式与批量更新方式遵守本宪法中的特别规定

## 设计哲学

### 实例是什么

- 一个 Mass Entity 对应一个实际存在的 BBBInstance
- 实例拥有自己的身份 配置 运行状态与生命周期
- Mass 负责这些实例的数据存储与批量调度
- Processor 负责根据实例状态维护对应行为
- 表现对象负责显示实例已经成立的结果

进一步说明

- 实例存在 不代表它必须拥有一个 Actor
- 实例存在 不代表它必须拥有一个 UObject
- 实例存在 不代表它必须拥有独立的 Tick
- 表现对象不存在 不代表实例不存在
- 表现对象被回收 不得导致实例丢失玩法状态

### 与 Actor 的关系

BBBActor 与 BBBMassInstance 使用一致的理解方式

- 外部通过输入影响实例
- 输入解析后写入实例状态
- 各领域根据状态维护行为并产生结果
- 网络观察已经成立的结果
- 表现读取已经成立的状态

两者允许因为运行载体不同 使用不同的数据布局与调度方式

禁止为了形式统一 给每个 Mass 实例创建一套独立的系统对象与更新对象

禁止为了使用 Mass 再创造一套与本项目无关的玩法语义

## 物理文件构造

全部 Mass 实例及其必要的公共实现收敛于 `UBBBNexus/Mass/`

```text
Mass/
    Core/                              当前实例共同需要的世界级管理与生命周期设施
    Network/                           共用的 UE 网络传输边界

    Projectile/                        子弹实例
        Config/                        静态配置
        Input/                         外部输入包
        Logic/
            Core/                      初始化 更新阶段与关闭规则
            System/
                XxxSystem/
                    DomainData/        领域 Fragment
                        States/        领域状态
                        Definitions/   必要的领域数据结构
                        Context/       必要的临时上下文
                    Processors/        批量处理的具体实现
        Presentation/                  子弹表现桥接

    Monster/                           小怪实例
        Config/
        Input/
        Logic/
            Core/
            System/
                XxxSystem/
                    DomainData/
                        States/
                        Definitions/
                        Context/
                    Processors/
        Presentation/
        Spawning/
```

- 只创建当前实际需要的文件与目录
- 公共目录只容纳已经存在的共同需求
- 禁止为了未来可能出现的实例提前设计注册体系与通用消息框架
- System 表示领域职责 不要求每个实例持有一个 System 对象
- 具体逻辑必须下沉到对应领域的 Processor
- 对外只暴露当前需要的输入入口 配置类型与只读查询
- 实例之间禁止依赖对方的内部 Fragment 与 Processor

## 数据构造的特别规定

### 总原则

Mass 按数据类型批量存储实例状态

因此本目录不要求通过一个实体内部的 `RuntimeData` 对象直接持有全部领域

本节替代数据宪法中关于 C 直接持有 B 以及必须通过 C 到 B 到 A 访问的规定

数据宪法中关于领域划分 写入责任 只读访问 纯数据容器与生命周期的原则继续生效

### 领域持有者 B

- B 是一个由 Mass 存储的领域 Fragment
- B 继承 `FMassFragment`
- B 继续使用 `DomainState` 作为命名后缀
- B 直接私有持有所属领域的状态 A
- B 为每个需要外部读取的 A 提供对应的 const 读取方法
- 读取方法使用 `Read` 加完整状态语义命名
- 负责维护 A 的 Processor 必须由 B 显式声明为 friend
- 领域外对象禁止取得 A 的可写引用
- B 禁止拥有玩法逻辑与外部调用

### 状态 A 与自定义数据 O

- A 继续以 `State` 作为命名后缀
- A 由所属 B 直接构造并持有
- O 由所属 A 直接构造并持有
- A 与 O 都是纯数据
- 每个具体数据结构独占一个头文件
- 禁止把配置 运行状态 输入缓存与网络传输状态混成一个无法区分职责的结构
- 禁止仅为了拆文件 将生命周期与维护责任相同的数据切成大量零碎状态

### 聚合黑板 C

在 Mass 中 一个 Entity 所拥有的全部领域 Fragment 在逻辑上共同构成它的运行时黑板

不额外创建一个持有全部领域副本的 C

```text
Mass Entity
    领域 Fragment B
        状态 A
            必要的数据 O

    另一个领域 Fragment B
        状态 A
```

Processor 通过 Mass Query 取得本次更新需要的领域 Fragment

取得 Fragment 后 继续遵守对应领域的读写权限

禁止为了恢复 Actor 的物理持有形式 将全部领域重新塞入一个巨大的 RuntimeData Fragment

禁止让一个 Processor 为了读取少量数据而无条件取得全部领域的写权限

### 临时上下文 D

- D 继续使用 `Context` 作为命名后缀
- D 只在本次处理期间构造与使用
- D 可以引用本次查询已经取得的 Fragment
- D 不拥有被引用的持久状态
- D 不得跨帧保存
- Fragment 引用不得跨越实体结构变化或生命周期边界保存
- 禁止为了统一调用形式增加无实际用途的 Context

### 引擎数据与静态配置

- UE 要求的标准 Fragment 按引擎规则存储
- 同一份玩法状态必须明确唯一维护来源
- 如果表现或引擎接口需要副本 必须明确其只读快照或单向同步性质
- 禁止在业务状态与引擎 Fragment 中各自独立维护两套位置 速度或生命值

- 配置是静态数据
- 运行状态属于具体 Entity
- 相同配置可以被多个 Entity 共享
- 禁止为了保存每只怪的当前血量或每颗子弹的剩余寿命 克隆一份配置资产
- 不同实例的运行状态不得通过共享配置互相污染

## 输入与外部交互

### 统一入口

BBBMassInstance 对外提供与 BBBActor 一致的输入语义

```cpp
template<typename TPacket>
bool SubmitInput(TPacket &&Packet);
```

- 输入入口可以由轻量的实例引用提供
- 实例引用必须能够确认所属世界与目标 Entity 是否仍然有效
- 禁止为了提供这个方法 为每个 Entity 分配独立的 UObject 或堆对象
- 外部禁止绕过输入入口直接修改实例的领域状态
- 实例创建与回收由生命周期设施负责 不伪装成对一个尚不存在实例的普通行为输入

### 输入包

- 输入包为 final 结构体
- 每种输入包独占一个头文件 不写 cpp
- 成员由数据字段 `IsValid` `CanApply` 与 `Apply` 构成
- 输入包不保存跨次调用的执行状态
- `IsValid` 与 `CanApply` 只能读取输入值与允许读取的状态
- `Apply` 只能写入明确允许修改的状态
- `Apply` 可以进行无副作用的值计算
- 输入包禁止调用 UE 执行接口
- 输入包禁止直接发射子弹 播放表现 发送 RPC 或销毁实体
- 输入包禁止直接调用其它系统或 Processor

### 输入来源

```text
Input/
    LocalControl/      本机产生的输入与结果
    RemoteMessage/     远端投送来的待接收结果
    AuthorityFact/     房主分发的当前事实
```

- 第三级按照影响领域划分
- 具体输入包位于第四级
- 命名使用作用语义加所属来源加 Packet
- 不同来源的输入分别定义 禁止为了代码复用混用包类型

重要

输入来源与目标实例的控制归属不是同一个概念

例如 本机子弹命中房主控制的小怪

这个命中可以作为本机产生的输入进入小怪

不代表本机因此取得小怪的寻路与攻击控制权

### 输入槽位

- 每个目标实例的每种输入包只有一个有效槽位
- 槽位只保存 bActive 与当前输入包
- 解析阶段按明确顺序消费槽位
- 同一目标在一次解析前收到同种输入 后来者覆盖先来者
- 此规则不得改变

需要累计的业务必须在所属领域明确形成累计结果

禁止通过让输入槽位追加历史事件 或在普通动作包内暗藏无限事件列表 绕过覆盖规则

不同实例的槽位必须互相独立

实例回收后 尚未消费的输入不得作用于复用该存储位置的新实例

## 批量更新与生命周期

### 更新职责

- 更新阶段与依赖由 Core 明确
- 具体批量执行交给 Mass 调度器
- Processor 必须声明实际使用的数据及其读写权限
- 同一状态的多个写入阶段必须具有明确顺序
- 禁止依赖处理器恰好以某种顺序注册

- 初始化负责建立有效的身份 配置引用与初始状态
- 解析负责将输入效果写入状态
- 玩法领域负责维护行为并生成结果
- 网络负责观察与传输已经成立的结果
- 表现负责消费状态
- 关闭负责收束引用 表现与待处理输入

以上是职责边界 不要求为每个职责增加独立的逐实例对象

### 线程边界

- 纯数据计算优先按 Mass 批量处理
- 调用 UObject 场景查询 网络与表现接口时必须遵守对应线程要求
- 禁止仅因为使用 Mass 就假定 UE 接口可以在工作线程调用
- 禁止从未声明的数据访问路径取得可写状态
- 批量遍历期间的实体创建 销毁与组成变化必须使用引擎允许的安全时机

### 生命周期边界

- 实例的逻辑生命周期与表现对象的生命周期分开
- 子弹离开枪口后具有自己的生命周期
- Rifle 被切换或销毁 不得使已经成立的子弹丢失玩法归属
- 小怪表现被隐藏或回收 不得删除它的生命与行动状态
- 失效实体引用必须被拒绝并在关键边界提供可定位的日志

## 网络权责

### 基本模型

沿用 Actor 的四类网络身份

- X 表示由本机控制 包括间接控制
- Y 表示不由本机控制
- M 表示本机是房主
- N 表示本机是客机

| 分类 | 身份 |
|---|---|
| 甲 | XM |
| 乙 | XN |
| 丙 | YM |
| 丁 | YN |

- 本机控制决定是否能够产生对应行为的因果结果
- 房主身份决定网络接收与分发职责
- 禁止使用房主身份直接替代玩法控制权
- 禁止因为一个实例是镜像 就禁止它接收来自本机其它实例的合法影响
- 禁止因为镜像需要执行表现 就允许它重复产生对应玩法结果

网络身份在实例边界统一确定

领域 Processor 只使用执行该领域所需的明确权限

禁止各领域自行查询并解释一套不同的网络身份

### 网络传输

- 网络只观察已经成立的状态与结果
- 网络接收转换成输入
- 网络不得重新执行发送方已经完成的玩法因果
- 房主允许检查实例身份 数据结构 数值有效性与消息新旧
- 房主不得把已经成立的本机操作重新变成待批准请求

- 谁拥有业务 谁定义结果的含义与接收方式
- 可以共享网络载体
- 共享载体不得承担子弹伤害或小怪生命等内部玩法判断
- 多来源结果的业务合并由所属领域处理
- 网络发送缓存与传输版本不得冒充玩法状态

### 身份与收敛

- 需要跨机器识别的实例必须具有稳定的网络身份
- 本地 Mass Entity 的槽位下标不能直接作为跨机器身份
- 实例复用必须能够区分新旧生命周期
- 同一结果重复收到不得重复生效
- 迟到结果不得作用于错误实例
- 当前状态必须能够在通信恢复后继续收敛
- 禁止为了弱一致同步保存无必要的完整历史

## 子弹实例

- 子弹出生时根据发射来源确定玩法归属
- 本机拥有该次发射因果的子弹可以产生命中结果
- 其它机器上的对应子弹只还原表现
- 镜像子弹不得再次扣血 生成奖励或产生其它世界结果

- 发射结果包含还原当前弹道所需的最少信息
- 远端不得使用接收时的新枪口朝向替代已经确定的发射方向
- 允许丢弃过期射击表现
- 禁止为了补全历史表现重新执行过去的开火逻辑

- 子弹可以没有实体网格
- 弹道与碰撞由逻辑维护
- 光迹 火花与其它视觉效果由表现维护
- Niagara 的显示结果不得作为玩法命中的唯一依据
- 子弹表现应批量提交
- 禁止默认给每颗子弹创建独立 Actor Tick 或动态光源

## 小怪实例

### 行动

- 小怪的目标选择 寻路 移动决策与攻击决策由房主产生
- 客机接收并表现已经成立的行动结果
- 客机允许平滑收到的移动结果
- 客机禁止自行重新寻路或重新裁决相同攻击
- 房主禁止在同一帧无预算地集中处理全部小怪的昂贵查询

### 受击与生命

- 本机拥有玩法权的来源造成伤害时 本机立即应用该结果
- 本机致死时立即进入死亡状态
- 房主接收已经成立的伤害与死亡结果并分发
- 不等待房主重新进行命中判定

- 多个来源对同一只怪造成的有效伤害必须能够合并
- 禁止用互相覆盖的剩余血量丢掉其它来源已经造成的伤害
- 同一份伤害不得因重传重复扣除
- 结果合并只维护当前需要的最少状态
- 禁止借此引入预测 回滚与完整事件重演

### 死亡

- 当前没有复活玩法
- 同一代实例的死亡一旦成立不得被旧的存活结果覆盖
- 本地死亡后立即停止该实例在本机的有效碰撞与行动
- 死亡表现可以继续存在
- 新出生的小怪是新的实例
- 旧实例的伤害与死亡消息不得影响新实例

### 碰撞与表现

- 小怪的有效碰撞范围属于逻辑状态
- 命中判定不得依赖表现 Actor 是否存在
- 表现 LOD 与可见性不得改变小怪能否被命中的事实
- 表现 Actor 只承担必要的 UE 表现桥接
- 表现 Actor 不持有第二套生命值 行为决策与网络权威

## 简化原则

本目录的目标是用 Mass 高效承载当前需要的 BBBInstance

- 不为形式统一增加运行时对象
- 不为未来可能的玩法增加空系统
- 不为不同实例强行建立公共继承层
- 不为少量消息建立通用消息总线
- 不将每次输入保存成永久事件
- 不复制 UE 已经提供的存储 调度与批量表现设施
- 不以目录数量 类数量或抽象层数作为架构完成标准

新增结构必须能够说明它解决了当前哪一个具体问题

删除这个结构后如果只是少了一次转发 就不应该保留这个结构
